# DESIGN.md Standard

Status: Adopted for Frontend Design Guardian pilots. A DESIGN.md is a versioned design contract, not a replacement for product discovery or visual verification.

## Required Structure

Every project DESIGN.md must contain these sections in order: Product identity; Business objective; Audience; Brand personality; Visual references; Typography system; Color system; Spacing scale; Grid and layout; Components; Borders and radius; Elevation and shadows; Icons; Photography and artwork; Motion; Responsive rules; Accessibility rules; Conversion hierarchy; Forbidden patterns; Acceptance criteria.

Values must be semantic and implementable. Colors include role and contrast intent. Type includes family, size, weight, line height, and usage. Layout includes constraints and collapse behavior. Components include states and accessibility behavior. Acceptance criteria identify the project threshold and evidence paths.

## Governance

- Validate DESIGN.md before implementation.
- Preserve workspace brand autonomy while sharing behavioral and accessibility foundations.
- Record references as inspiration, not copied brand identity.
- Keep desktop and mobile decisions explicit.
- Update the contract when a recurring design rule changes.
- Reject acceptance when evidence, independent review, or unresolved blockers are missing.

## Forbidden Defaults

Generic purple gradients, excessive glass cards, random neon, identical card grids for every section, oversized empty hero areas, meaningless dashboard statistics, unverified testimonials, generic AI imagery, inconsistent icon styles, excessive animation, unreadable low-contrast text, and arbitrary font-size choices are forbidden defaults. A documented product-specific rationale is required for any exception.
