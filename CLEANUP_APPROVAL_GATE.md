# Cleanup Approval Gate Specification

This document defines the safety boundaries, input dependencies, approval categories, and manual sign-off matrices for local file quarantine curation within Brilliantaire OS under Phase 12B.

## 1. Purpose
The cleanup approval gate acts as a validation wrapper over staged duplicate indexes. It reads duplicate variant reports, parses quarantine index lists, filters files against a protected do-not-touch registry, and maps candidates to specific approval categories for human verification before any physical quarantine move occurs.

## 2. Security Boundaries

### Staging and Approval Gating Constraints
* **Approval-Only Switch:** Direct file deletion is completely disabled. No system unlinks or permanent file removes are permitted.
* **No File Movement:** Candidates are not moved into quarantine folders. This gate only generates verification checklists.
* **No Source Modification:** Code source files (under `src/`, `scripts/`, or config folders) are never modified.
* **No Secret Scanning:** Credentials files (`.env`, `.env.local`, `.mcp.local.json`) are completely bypassed.
* **Safe Command Router:** Commands must match exact script names registered in the router. Aliases are blocked.

### Input Report Dependencies
The gate relies on the following reports generated by Phase 12A:
1. `outputs/cleanup/reports/duplicate_scan_report_YYYY-MM-DD.md`
2. `outputs/cleanup/quarantine_index/cleanup_quarantine_index_YYYY-MM-DD.md`
3. `outputs/cleanup/review_lists/cleanup_review_list_YYYY-MM-DD.md`

## 3. Approval Categories
Candidates are classified into these categories during the audit pass:
* `approve_for_quarantine`      : High-confidence variants ready for staged quarantine.
* `needs_manual_review`         : Unclear files or medium-risk reports requiring manual sign-off.
* `do_not_touch`                : Protected configurations, logs, or core project files.
* `low_confidence_duplicate`    : Low confidence variant candidates.
* `stale_but_recent`            : Reports or logs created recently.
* `orphan_candidate`            : Metadata files without matching recording assets.
* `safe_to_ignore`              : Diagnostic or transient files.

## 4. Protected Do-Not-Touch Registry
The system automatically assigns `do_not_touch` status and blocks cleanup staging for files matching these patterns:
* Git internals (`.git/`)
* Dependencies (`node_modules/`)
* Large binaries (`models/`)
* Secret config keys (`.env`, `.env.local`, `.mcp.local.json`)
* Build and package definitions (`package-lock.json`, `package.json`, `Taskfile.yml`)
* Safe Command Router configurations (`config/commands.ts`)
* Core operating metadata (`SYSTEM_STATUS.md`, `PROJECTS.md`, `NEXT_ACTIONS.md`, `README.md`)

## 5. CLI Command Suite
The gate features these subcommands executed via the router:
* `classify`      : Scan Phase 12A inputs and output eligibility reviews.
* `approval-list` : Build a manual approval check matrix.
* `do-not-touch`  : Compile protected target registers.
* `summary`       : Output aggregated counts and system readiness check.
* `status`        : Print console status metric reports dashboard.

## 6. Future Quarantine Execution Boundary
Once the approval gate successfully parses inputs and compiles checklists, the system transitions to `READY` status. The operator must manually review `outputs/cleanup_approval/approval_lists/cleanup_approval_list_YYYY-MM-DD.md` and check the approval boxes `[x]` for eligible files. Downstream quarantine moves remain blocked until this approval checklist has been reviewed and signed off.
